## Instructions

### Analysis
Your analysis MUST start with a clear explanation of why you chose the priority level.

Then consider:
- What problem this task solves
- What the expected outcome should be
- Key risks or dependencies to be aware of
- What areas of the codebase are likely affected

Format your analysis like this:
**Priority Reasoning**: [1-2 sentences explaining why this priority was chosen, referencing the priority scale rules]

[Rest of your analysis]

If the task title or description is unclear, nonsensical, or appears to be a test input (e.g. random characters, placeholder text), state that the task needs clarification and cannot be meaningfully analyzed.

### Priority
Suggest a priority number from 1-100. IMPORTANT: most tasks should fall in the 31-50 range.

Priority scale:
- 1-10: Production emergency ONLY (active outage, data loss, security breach in progress)
- 11-30: High priority (blocking bugs, important security fixes, critical features)
- 31-50: Normal priority (standard features, improvements, most bug fixes) — THIS IS THE DEFAULT RANGE
- 51-70: Low priority (nice-to-have, minor improvements, non-blocking issues)
- 71-100: Backlog (cosmetic, documentation, minor cleanup)

Rules:
- When in doubt, assign priority 50.
- If the task is unclear, nonsensical, or a test input, assign priority 50.
- Priority 1-10 requires evidence of active production impact. Do NOT assign 1-10 for general bug fixes or features, no matter how important they sound.
- Priority 11-30 requires a clear blocking issue or security vulnerability. Most bug fixes belong in 31-50.

### Description
Rewrite the task description as a clear, actionable specification with:
- Problem statement
- Acceptance criteria (bullet points)
- Technical hints (if applicable)

If the original task is unclear or nonsensical, write: "Task needs clarification. Original input does not contain actionable requirements."

Keep it concise but complete.
